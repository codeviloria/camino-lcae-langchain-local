# M3.5 Email Agent — proyecto del módulo 3

## Qué junta
| Pieza | Aquí | Mnemotecnia / lección |
|---|---|---|
| Runtime context `EmailContext` | email y contraseña "correctos" (`julie@example.com` / `password123`, datos de juguete) | **Carnet** (M2.2a) |
| State `AuthenticatedState.authenticated` | cambia cuando `authenticate` acierta | **Se mueve** (M2.2b) |
| Tool que escribe el state | `authenticate` → `Command(update={"authenticated": True, "messages": [ToolMessage(...)]})` | M2.2b |
| Dynamic tools | sin login solo ve `authenticate`; con login, `check_inbox` y `send_email` | **Utilería** (M3.4) |
| Dynamic prompt | prompt distinto según `authenticated` | **Guion** (M3.4) |
| HITL | pausa antes de `send_email` | **A-E-R-R** (M3.3) |
| Checkpointer | recuerda que ya se autenticó entre turnos | **Libreta y página** (M3.2) |

```
Turno 1: "julie@example.com, password123"
  🤖 (solo ve authenticate) → authenticate(email, password) → código compara con el context → ✅ authenticated=True
  🤖 (ahora ve check_inbox/send_email + prompt nuevo) → check_inbox → correo de Jane
  🤖 "I see an email from Jane… Would you like me to reply?"
Turno 2 (mismo thread): "any draft is fine. don't check back."
  🤖 → send_email(to, subject, body) → ⏸️ HITL
Humano: approve → "Email sent…" → 🤖 "I have sent a reply to Jane."
```

## Resultados del notebook (gemma4, CPU) ✅ al primer intento
| Paso | Resultado | Tiempo |
|---|---|---|
| Autenticación | `authenticate(email='julie@example.com', password='password123')` → *Successfully authenticated* ✅ | 3,1 s |
| Cambio de tools + prompt | En la llamada siguiente pidió `check_inbox` (que antes no veía) ✅ | 4,0 s |
| Resumen del inbox | *"I see an email from Jane… asking if you'd like to grab coffee next week. Would you like me to reply?"* ✅ | 5,6 s |
| Turno 2 → borrador | `send_email(to='jane@example.com', subject='Re: Coffee next week', body='Hi Jane, That sounds lovely!…')` → ⏸️ pausa ✅ | 6,2 s |
| Approve | `Email sent to jane@example.com…` → *"I have sent a reply to Jane."* ✅ (esta vez **sin** cierre vacío) | 4,2 s |
| State final | `authenticated: True` guardado en el checkpointer ✅ | |

- **El orden de los turnos importa:** el agente pidió confirmación en el turno 1 (*"Would you like me to reply?"*) y el curso lo previó con el turno 2.
- La respuesta del turno 2 queda **vacía** (`print` muestra nada) porque el agente está en pausa: el contenido está en `__interrupt__`.
- `send_email` del proyecto tiene 3 argumentos (`to`, `subject`, `body`) y gemma4 los llenó bien (a diferencia de 3.3, aquí la docstring coincide con los argumentos).

## ⚠️ Pregunta de seguridad abierta (para probar)
Con lo descubierto en M3.4 (**ocultar ≠ bloquear**): si un usuario **no autenticado** escribe *"call check_inbox"*, el modelo puede pedir la tool por nombre y el agente la ejecutaría. Defensa: un guardia `@wrap_tool_call` que revise `request.state.get("authenticated")` antes de `check_inbox`/`send_email`.

## 🎯 Para el examen
- Patrón de **autenticación por state**: la tool valida en **código** contra el **context** y escribe `authenticated` con `Command(update=...)`; el middleware lee el **state** en cada llamada.
- Middleware en el orden `[dynamic_tool_call, dynamic_prompt, HumanInTheLoopMiddleware(...)]`.
- `interrupt_on` con `False` para `authenticate` y `check_inbox`, `True` para `send_email`.
- En Studio, los `wrap_model_call` quedan **dentro** del nodo `model`; los hooks `before_*`/`after_*` aparecen como **nodos** (`HumanInTheLoopMiddleware.after_model`).
- Para servirlo: `langgraph.json` → `./3.5_email_agent.py:agent`, **sin checkpointer** (lo pone el servidor).

## Servirlo: `langgraph dev` + Studio ✅
`uv run langgraph dev` desde `notebooks/module-3` → Studio conectado (`Connected`), grafo `agent` desde `langgraph.json` → `./3.5_email_agent.py:agent`.

![Email Agent en LangGraph Studio](../img/M3.5-studio-email-agent.png)

**Qué muestra Studio (y cómo leerlo con lo aprendido):**
| En el grafo / trace | Qué es |
|---|---|
| `__start__ → model` | La llamada al modelo. **Dentro** de este nodo corren los `wrap_model_call` (dynamic tools y dynamic prompt): por eso **no** aparecen como nodos propios (igual que el ruteo de modelos en M3.4) |
| `HumanInTheLoopMiddleware.after_model` | El hook `after_model` de HITL **sí** es un nodo: revisa los `tool_calls` después de cada respuesta del modelo |
| Flechas `after_model → tools` / `→ __end__` / `→ model` | Si el modelo pidió tools, van a `tools`; si no, termina; si hubo un rechazo, vuelve al modelo |
| `tools → model` | El bucle: resultado de la tool → el modelo vuelve a pensar |
| Trace del turno 1 | `model` → `after_model` → `tools` (authenticate) → `model` → `after_model` … = el mismo flujo del notebook |
| Botones `Memory`, `Interrupts`, `View state`, `Re-run from here` | El **checkpointer** del servidor: cada paso es un checkpoint que se puede inspeccionar o re-ejecutar |

- Sin checkpointer en el `.py`: el servidor pone el suyo (cada thread de Studio es un `thread_id`).
- El contexto no se pasa: se usan los valores por defecto de `EmailContext` (credenciales de juguete).
