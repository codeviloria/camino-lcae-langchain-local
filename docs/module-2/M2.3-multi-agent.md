# M2.3 Multi-Agent

## Resumen
- Patrón **subagents as tools**: un agente principal tiene como tools funciones que **invocan a otros agentes**.
- Cada subagente tiene sus propias tools, prompt y contexto. El principal solo ve la respuesta final del subagente, no su historial interno, así que **aísla el contexto**.
- En el notebook: `subagent_1` (raíz cuadrada) y `subagent_2` (cuadrado), y `main_agent` decide a cuál llamar.

## Código clave
```python
@tool
def call_subagent_1(x: float) -> float:
    """Call subagent 1 in order to calculate the square root of a number"""
    response = subagent_1.invoke({"messages": [HumanMessage(content=f"Calculate the square root of {x}")]})
    return response["messages"][-1].content

main_agent = create_agent(model=MODEL, tools=[call_subagent_1, call_subagent_2], system_prompt="...")
```

## Por qué usar subagentes
- **Contexto limpio:** el ruido de las tools del subagente (por ejemplo el JSON de Kiwi, ver [M2.1b Travel Agent](M2.1b-travel-agent.md)) no llega al principal.
- **Especialización:** prompts y tools distintos por tarea.
- **Costo:** más llamadas al modelo. En CPU, una pregunta sencilla dispara ≥4 llamadas.

## Resultados ✅
Pregunta: *"What is the square root of 456?"*

```
main_agent ──tool_call──▶ call_subagent_1(x=456)
                              └─ subagent_1 ──▶ square_root(456) ──▶ "The square root of 456.0 is approximately 21.354."
main_agent ◀──ToolMessage──── (solo el texto final del subagente)
main_agent ──▶ "The square root of 456 is approximately 21.354."   ✅ (√456 = 21,3542)
```

| Paso | Tokens entrada | Tiempo |
|---|---|---|
| Principal → elige `call_subagent_1(x=456)` | 155 | 3,9 s |
| Subagente 1 completo (modelo → `square_root` → modelo) | — | ~2–3 s |
| Principal → respuesta final | 203 | 2,1 s |
| **Total** | | **~8 s** |

**Lo que confirma:**
- **Aislamiento de contexto:** en `response["messages"]` del principal hay solo **4 mensajes**. Los mensajes internos del subagente (su tool call a `square_root` y su `ToolMessage`) **no aparecen**: el principal solo ve el `return` de `call_subagent_1`.
- El principal eligió bien entre los dos subagentes **solo por la docstring** de la tool ("…calculate the square root…").
- El modelo convirtió la pregunta en `x=456` (argumento tipado `float`).
- Detalle: la tool declara `-> float` pero devuelve **texto** (`response["messages"][-1].content`). LangChain no valida el tipo de retorno; el `ToolMessage` siempre es texto.
- Para ver el trabajo interno del subagente hay que ir a **LangSmith**: el trace muestra el subagente **anidado** dentro del run de la tool.

## 🎯 Para el examen (dominio Build)
- **Patrón "subagents as tools":** se envuelve `subagent.invoke(...)` dentro de una función `@tool`. El principal ve **solo la docstring** (para decidir) y **solo el return** (como `ToolMessage`).
- **Ventaja principal: aislamiento de contexto.** El historial y los resultados intermedios del subagente no ensucian el contexto del principal (ver el desborde de [M2.1b Travel Agent](M2.1b-travel-agent.md)).
- **Costo:** cada nivel suma llamadas al modelo. Aquí, 1 pregunta = **4 llamadas** (2 del principal y 2 del subagente).
- **Cada subagente es un `create_agent` independiente**, con su modelo, tools y system prompt propios (se pueden usar modelos distintos por subagente).
- **La docstring de la tool-subagente es el "contrato"**: si es ambigua, el principal elige mal.
- **Qué devolver al principal:** normalmente `response["messages"][-1].content` (respuesta final). Devolver todo el historial anularía el aislamiento.
- **Paso de datos sin prompt:** el subagente puede recibir datos del state del principal con `runtime.state` (lo usa M2.4 Wedding Planner).
- **Relación con Deep Agents (curso 02):** los subagentes son una pieza central de `deepagents`. Esta es la versión "manual" del patrón.
- **Pregunta trampa probable:** "¿El agente principal ve las tool calls internas del subagente?" → **No**, solo el valor que devuelve la tool que lo envuelve. Para depurar, se mira el trace anidado en LangSmith.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | El historial del principal no muestra lo que hizo el subagente | Aislamiento de contexto: solo vuelve el `return` | Ver el trace anidado en LangSmith | Depurar multi-agente = mirar el trace, no `response["messages"]` |
| 2 | La tool declara `-> float` y devuelve texto | LangChain no valida el retorno; el `ToolMessage` es texto | Tipar `-> str` para ser honesto | El tipo de retorno no forma parte del esquema que ve el modelo; los args sí |
| 3 | 4 llamadas al modelo para una raíz cuadrada | Cada nivel de agente agrega su loop | Usar subagentes cuando la tarea lo justifique (contexto pesado o especialización) | Multi-agente = más latencia y costo; en CPU se nota |

## Trampas para el examen
- Subagente = agente envuelto en una `@tool`. La docstring de esa tool es lo que el principal usa para decidir.
- El principal **no** ve los mensajes internos del subagente, solo el `return`.
- Relación con Deep Agents (curso 02): los subagentes son una pieza central ahí.
