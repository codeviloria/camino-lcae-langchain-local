# M3.3 Human-in-the-Loop (HITL)

## Qué es (en una frase)
Un **mockup** de asistente de correo: dos tools falsas (`read_email` lee el correo del **state**; `send_email` solo dice *"Email sent"*) y un **middleware** que pone un **semáforo** antes de `send_email`. El agente se detiene, un **humano** decide y el agente sigue.

```
usuario ─► modelo pide read_email ─► (sin pausa) ─► modelo pide send_email
                                                     │
                                         ⏸️  HumanInTheLoopMiddleware (after_model)
                                                     │  interrupt() → checkpointer guarda todo
                                         humano decide: approve | edit | reject | respond
                                                     │  Command(resume=..., mismo thread_id)
                                                     ▼
                                         se ejecuta (o no) la tool → el modelo cierra
```

## Piezas
| Pieza | Para qué |
|---|---|
| `EmailState(AgentState)` con `email` | El correo entra por el **state**, no por una API (mockup) |
| `checkpointer=InMemorySaver()` | **Obligatorio**: sin él no se puede pausar y reanudar |
| `interrupt_on={"read_email": False, "send_email": True}` | Qué tools llevan semáforo |
| `response["__interrupt__"]` | Aparece **solo** si hubo pausa: qué quiere hacer y qué decisiones se permiten |
| `Command(resume={"decisions": [...]})` + mismo `config` | La respuesta del humano a la pausa |

**Decisiones permitidas** (las vi en el interrupt real): `['approve', 'edit', 'reject', 'respond']`. `respond` no sale en el curso: el humano contesta **en lugar de** la tool.

### Corrida 3 (prompt con la línea 3 de reintento) — flujo completo
| Paso | Resultado |
|---|---|
| Borrador | *"Hi John, Thanks for letting me know. Let's find another time that works for both of us. Best, Seán."* |
| Reject (*"No please sign off - Your merciful leader, Seán."*) | ✅ **Reintentó**: nueva pausa (`¿Nueva pausa? True`). ⚠️ Pero el borrador nuevo fue **idéntico**: no aplicó la crítica |
| Edit sobre esa nueva pausa | Se envió mi texto → `Email sent` → cierre vacío |
| Dataset (`decidir()`) | 3 ejemplos JSONL: approve, edit (con `correccion_humana`) y reject (con `motivo_rechazo`) ✅ |

Flujo real del thread, con `ver(response)`:
```
[3] 🤖 pide send_email("Hi John, Thanks…")
[4] ⛔ RECHAZADA: No please sign off - Your merciful leader, Seán.
[5] 🤖 pide send_email("Hi John, Thanks…")   ← reintentó, pero igual
[5'] (Edit humano) → "This is the last straw, you're fired!"
[6] 🔧 Email sent
[7] 🤖 (respuesta vacía)
```
> Nota de uso: la celda `nueva_pausa("edit")` tenía la salida de la corrida anterior (no la volví a correr), así que el Edit se aplicó a la pausa pendiente del thread `reject`. Resultado útil: **rechazo → reintento → edición → envío** en una sola conversación.

**Errores de uso que me pasaron (y su explicación):**
- `pprint(response)` mostraba la respuesta **vieja**: había recreado el agente pero no volví a correr el `invoke`. → En Jupyter, una variable guarda el último valor **asignado**; el número `[n]` dice el orden en que corrió cada celda, no su posición.
- Reject y Edit "no hicieron nada" la primera vez: la pausa ya se había consumido con Approve. → Cada decisión **consume** la pausa; para probar otra, hace falta un `invoke` nuevo (lo resolví con un helper `nueva_pausa(thread_id)`, un thread por decisión).

**Diferencia de versión (para no confundirse):** en mi entorno, Edit reescribió el `tool_call` del `AIMessage` y Reject guardó mi mensaje tal cual. En LangChain 1.4.3 el historial conserva la llamada original del modelo (la edición se aplica al ejecutar) y el rechazo llega como *"User rejected the tool call for `send_email` with reason: …"*. El concepto no cambia.

## 🧒 Leer `pprint(response)` sin perderse
`response` = dict con **3 llaves**: `__interrupt__` (solo si hay pausa), `email` (el state extra) y `messages` (la conversación). `pprint` corta a 80 caracteres y por eso parte los textos palabra por palabra.
| Mensaje | Mira | Ignora |
|---|---|---|
| `HumanMessage` | `content` | `id`, `additional_kwargs` |
| `AIMessage` | `content` y **`tool_calls`** | `response_metadata`, `usage_metadata` |
| `ToolMessage` | `content`, `name`, `status='error'` | `tool_call_id` |

`AIMessage(content='', tool_calls=[...])` = el modelo **no habló, pidió una tool**. En el notebook dejé `ver(response)`: una línea por mensaje + la pausa y sus decisiones.

## 💡 Idea propia: HITL como fuente de datos para entrenar
Cada decisión del humano es una etiqueta de experto:
| Decisión | Dato | Técnica |
|---|---|---|
| `approve` | (entrada, borrador) = ejemplo bueno | SFT |
| `edit` | (entrada, borrador → versión corregida) | SFT con la corrección; par preferido/rechazado |
| `reject` + motivo | (entrada, borrador malo, crítica) | Preferencias (DPO/RLHF) y casos de evaluación |
| `respond` | (pregunta del agente → respuesta humana) | Ejemplos para tools de "preguntar al usuario" |

Ciclo: **producción → feedback humano → dataset → evaluación / fine-tuning → mejor modelo**. En LangSmith: *feedback*, *annotation queues* y *datasets* (cursos 03 y 04). En el notebook, `decidir()` guarda el borrador y la decisión **antes** de reanudar y arma un JSONL.
Cuidados: anonimizar datos personales, volumen y calidad, y separar un conjunto de evaluación.

## 🧠 Lecciones aprendidas
| # | Observación | Regla |
|---|---|---|
| 1 | Sin `tool_calls` no hay pausa | **HITL solo protege lo que el modelo pide.** Verificar `"__interrupt__" in response` |
| 2 | Una docstring que menciona un dato que la tool no recibe confundió al modelo | La docstring es la interfaz: debe coincidir con los argumentos reales |
| 3 | Reject: el modelo se rindió en vez de reescribir | Decir en el prompt qué hacer tras un rechazo ("rewrite and call send_email again") |
| 4 | Cada decisión consume la pausa | Un `invoke` (o thread) nuevo por cada prueba |
| 5 | Cierres vacíos de gemma4 tras una tool | Validar el último mensaje; pedir confirmación final en el prompt |
| 6 | El detalle del historial tras Edit/Reject cambió entre versiones | Aprender el **concepto**; verificar el detalle en la versión instalada |
| 7 | Con la línea 3, reintentó tras el Reject pero repitió el mismo borrador | Pedir reintentar ≠ que use la crítica. Más explícito: *"incorporate the user's feedback verbatim"*, o usar `edit` cuando el humano ya sabe qué quiere |
| 8 | Una salida vieja hizo creer que había una pausa nueva | Verificar `config` (thread) y el número `[n]` de la celda antes de reanudar |

## 🎯 Para el examen
- HITL vive en **`after_model`**: revisa los `tool_calls` del `AIMessage` y llama a `interrupt()`.
- **Requiere checkpointer** y se reanuda con `Command(resume={"decisions": [...]})` en el **mismo `thread_id`**.
- `interrupt_on`: `True` (todas las decisiones), `False` (sin pausa) o `{"allowed_decisions": [...]}`; tools no listadas se aprueban solas.
- Decisiones: `approve`, `edit` (`edited_action` con `name` y `args`), `reject` (`message` → `ToolMessage` con `status="error"`), `respond`.
- Varias tools en una respuesta → **una decisión por `action_request`**, en orden.
- Ruta del borrador: `response["__interrupt__"][0].value["action_requests"][0]["args"]["body"]`.
- **Trampas:** reanudar sin pausa pendiente no hace nada; HITL no se activa si el modelo no pide la tool; sin checkpointer no hay reanudación.
