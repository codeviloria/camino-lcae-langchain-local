# M1.5 Memory

## Resumen
- Un agente **sin memoria** trata cada `invoke` como una conversación nueva: no recuerda nada de la llamada anterior.
- La memoria de corto plazo se activa con un **checkpointer**: `create_agent(model, checkpointer=InMemorySaver())`.
- Cada conversación se identifica con un **`thread_id`** que se pasa en el `config` de cada `invoke`.
- Con el mismo `thread_id`, el agente recarga el historial y lo envía completo al modelo en cada turno.

## Experimento: sin memoria vs con memoria
| | Sin checkpointer | Con `InMemorySaver` + `thread_id="1"` |
|---|---|---|
| Turno 1: "My name is Seán, my favourite colour is green" | Saluda normal | Saluda normal |
| Turno 2: "What's my favourite colour?" | "I can't read your mind…" ❌ | "Your favorite color is green! … Seán" ✅ |
| Mensajes en la respuesta del turno 2 | 2 | 4 (incluye el turno 1) |
| Tokens de entrada del turno 2 | 22 | **91** |

> La "memoria" no es magia: es **reenviar el historial** al modelo. Por eso los tokens de entrada crecen en cada turno.

## Código mínimo
```python
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent
from langchain.messages import HumanMessage

agent = create_agent(get_model(), checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "1"}}

agent.invoke({"messages": [HumanMessage("Hello my name is Seán and my favourite colour is green")]}, config)
agent.invoke({"messages": [HumanMessage("What's my favourite colour?")]}, config)   # → green
```

## Conceptos clave
| Concepto | Qué es | Nota |
|---|---|---|
| Checkpointer | Guarda el estado del grafo después de cada paso | Viene de **LangGraph** (`langgraph.checkpoint`) |
| `InMemorySaver` | Checkpointer en RAM | Se pierde al reiniciar el kernel. Solo para pruebas |
| `thread_id` | ID de la conversación | Otro `thread_id` = conversación nueva, sin historial |
| Memoria corto plazo | Historial dentro de un thread | La de esta lección |
| Memoria largo plazo | Datos que sobreviven entre threads (`store`) | Tema aparte |

## Producción
- `InMemorySaver` → solo desarrollo.
- Persistente: `SqliteSaver` (`langgraph-checkpoint-sqlite`) o **`PostgresSaver`** (`langgraph-checkpoint-postgres`). Encaja con mi stack PostgreSQL.
- En LangSmith Deployment la persistencia la da la plataforma (threads y runs) → dominio **Deploy**.

## Multiusuario: cómo asociar conversaciones y memoria a cada usuario
Dos niveles de memoria, cada uno con su clave:

| Nivel | Clave | Qué guarda | Herramienta |
|---|---|---|---|
| **Una conversación** | `thread_id` | Historial de mensajes de ese chat | Checkpointer (`PostgresSaver`) |
| **Un usuario** (entre conversaciones) | `user_id` | Lo que debe sobrevivir a todos sus chats: nombre, preferencias, contexto | Store (`PostgresStore`), namespace `(user_id, "memories")` |

### Flujo
1. **El backend crea el `thread_id`** (UUID) y lo registra en su propia tabla:
   ```sql
   CREATE TABLE conversations (
     thread_id UUID PRIMARY KEY,
     user_id   TEXT NOT NULL,
     titulo    TEXT,
     creado    TIMESTAMPTZ DEFAULT now()
   );
   ```
   Así se sabe qué hilos tiene cada usuario y se puede listar su historial.
2. **En cada mensaje:** autenticar al usuario (JWT/sesión) → verificar que el `thread_id` le pertenece → invocar:
   ```python
   config = {"configurable": {"thread_id": thread_id, "user_id": user_id}}
   agent.invoke({"messages": [HumanMessage(texto)]}, config)
   ```
3. **Checkpointer persistente y compartido** (`PostgresSaver`): todos los workers/réplicas ven el mismo estado. `InMemorySaver` no sirve: cada proceso tendría su propia memoria y se pierde al reiniciar.
4. **Memoria de largo plazo:** un chat nuevo empieza con historial vacío, pero puede leer del store lo que se sabe del usuario.

### Seguridad
- **Nunca confiar en un `thread_id` enviado por el cliente sin validarlo.** Si alguien adivina o reutiliza el ID de otro, lee su conversación. Verificar siempre `thread.user_id == usuario_autenticado`.
- **El `user_id` sale de la autenticación**, nunca del cuerpo del request.
- En **LangSmith Deployment** esto lo cubren *authentication* (quién eres) y *authorization* (a qué threads accedes) → dominio **Deploy** del examen.

### Aplicado al RF Optimization Copilot
- `user_id` = cada ingeniero de optimización.
- `thread_id` = cada caso investigado (ej. "degradación celda BAQ123").
- Store del ingeniero: su región, vendor y umbrales preferidos.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | Sin checkpointer, el agente no sabía el color favorito | Cada `invoke` es independiente | `checkpointer=InMemorySaver()` + mismo `thread_id` | Memoria = checkpointer + thread_id; sin los dos no hay memoria |
| 2 | El turno 2 con memoria leyó 91 tokens vs 22 sin memoria | El historial completo se reenvía en cada turno | Normal; en conversaciones largas hay que recortar o resumir | En CPU, **la memoria también es latencia**; con `num_ctx=8192` el historial tiene techo |
| 3 | La primera llamada tardó 25 s (16 s de `load_duration`) | El modelo se había descargado de RAM | Normal tras >5 min sin uso | Primera llamada lenta = carga del modelo, no el código |
| 4 | `ModuleNotFoundError: local_model` | El notebook está en una subcarpeta y `local_model.py` en la raíz | Celda con `sys.path.insert` que busca `local_model.py` en las carpetas padre | Ver [00 Setup lab local](../setup-lab-local.md) |

## Trampas para el examen
- El checkpointer se pasa al **crear** el agente; el `thread_id` se pasa en **cada** `invoke` (`config`).
- `InMemorySaver` no es para producción.
- Historial largo → riesgo de pasar la ventana de contexto → **context engineering** (recortar/resumir con middleware, ej. `SummarizationMiddleware`).
- Checkpointer (corto plazo, por thread) ≠ Store (largo plazo, entre threads).
