# M3.4 Dynamic models, prompts y tools (`wrap_model_call`)

Las tres lecciones usan **el mismo mecanismo**: un middleware que se mete **en cada llamada al modelo** y cambia algo del `ModelRequest` antes de llamar a `handler(request)`.
| Notebook | Qué cambia | Con qué |
|---|---|---|
| `3.4_dynamic_models` | el **modelo** | `request.override(model=...)` |
| `3.4_dynamic_prompts` | el **system prompt** | `@dynamic_prompt` (atajo sobre `wrap_model_call`) |
| `3.4_dynamic_tools` | las **tools visibles** | `request.override(tools=[...])` |

```python
@wrap_model_call
def mi_middleware(request: ModelRequest, handler) -> ModelResponse:
    # 1. leer: request.messages, request.state, request.runtime.context
    # 2. decidir y cambiar: request = request.override(model=... / tools=... / system_message=...)
    return handler(request)          # 3. llamar al modelo de verdad
```

## Dynamic models ✅ (`3.4_dynamic_models`)
**Regla:** más de 10 mensajes → `large_model` (`qwen3:8b`, 32K); si no → `standard_model` (`gemma4`). Es *model routing*.

| Caso | Mensajes | Modelo que respondió | Respuesta |
|---|---|---|---|
| Corto | 1 | `gemma4:latest` ✅ | Larga, en personaje de pasante, con emojis y acotaciones (*"I quickly look over to the office plant…"*) |
| Largo | 11 | `qwen3:8b` ✅ | Breve y práctica: trasplantar cuando las raíces salgan por los agujeros de drenaje, en unos meses |

- El ruteo funcionó en los dos casos: lo confirma `response_metadata["model_name"]`.
- Se nota el **estilo** distinto de cada modelo con el mismo system prompt: el cambio de modelo también cambia el tono.
- Con `reasoning=False` en `local_model.py`, qwen3 no gastó tokens pensando.

### ¿Por qué en LangSmith no se ve "la elección"?
El middleware **no es una tool**: no genera `tool_call` ni `ToolMessage`. Decide **dentro** de la llamada al modelo. Dónde verlo:
| Dónde | Qué mirar |
|---|---|
| La respuesta | `messages[-1].response_metadata["model_name"]` |
| LangSmith | Run del modelo (`ChatOllama`) → **Metadata** → `ls_model_name` (y *Invocation params* → `model`) |
| Log propio | Un `print`/logger dentro del middleware con el **motivo** de la decisión (celda EXTRA del notebook, con `tags=["M3.4-dynamic-models"]`) |

> En producción conviene **loguear el porqué** del ruteo (cuántos mensajes, qué tipo de usuario): el trace muestra qué modelo respondió, pero no la razón.

## Dynamic prompts ✅ (`3.4_dynamic_prompts`)
**Qué cambia:** el **system prompt**, no las tools ni el modelo. `@dynamic_prompt` lee `request.runtime.context.user_language` y devuelve el texto del prompt **antes de cada llamada**.

```python
@dataclass
class LanguageContext:              # el "carnet" que se trae al entrar
    user_language: str = "English"

@dynamic_prompt
def user_language_prompt(request):  # L-O-H: Leer → (Override automático) → Handler
    lang = request.runtime.context.user_language
    return "You are a helpful assistant." + ("" if lang == "English" else f" only respond in {lang}.")

agent = create_agent(model=MODEL, context_schema=LanguageContext, middleware=[user_language_prompt])
agent.invoke({"messages": [HumanMessage("Hello, how are you?")]}, context=LanguageContext("Irish"))
```

| `context` | Respuesta de gemma4 | Evaluación |
|---|---|---|
| `Irish` | *"Dia is Muire! Tá mé go maith, go raibh maith agat. Agus tú?"* | ✅ irlandés correcto (respuesta tradicional al saludo) |
| `Spanish` | *"Hola, estoy bien, gracias. ¿Y tú?"* | ✅ |
| `French` | *"Bonjour ! Je vais bien, merci. Et vous, comment allez-vous ?"* | ✅ |

- **Mismo mensaje, mismo agente, distinto carnet** → distinto idioma. Rápido (1 llamada al modelo, sin tools).
- **El system prompt dinámico no se guarda** en `response["messages"]`: `pretty_print` solo muestra Human y Ai. Se inyecta en cada llamada. Para verlo: input del run `ChatOllama` en LangSmith o el middleware "espía" del notebook (EXTRA).
- **Orden de middleware:** en `[user_language_prompt, espia]` el primero envuelve al segundo, así que el espía ve el prompt ya armado (verificado).

## 🧠 Mnemotecnias para estudiar
| Para recordar… | Mnemotecnia |
|---|---|
| Qué puede cambiar `wrap_model_call` | **Teatro:** el modelo es el **actor**; el middleware es el **asistente de camerino** que antes de cada escena cambia el **actor** (models), el **guion** (prompts) o la **utilería** (tools) |
| El patrón del código | **L-O-H:** **L**eer el request → **O**verride → **H**andler |
| Context vs State | **C**ontext = **C**arnet (lo traes al entrar, no cambia). **S**tate = **S**e mueve (las tools lo cambian) |
| Dónde se ve cada cosa | El **guion no se guarda** (system prompt dinámico fuera de `messages`); el **actor** se ve en `model_name`; la **utilería** solo se ve en lo que el modelo pudo pedir |

## 🧠 Lecciones aprendidas
| # | Observación | Regla |
|---|---|---|
| 1 | El cambio de modelo no aparece como paso visible del agente | El ruteo se audita por el metadata del run (`ls_model_name`) o con un log propio |
| 2 | Mismo prompt, estilos muy distintos (gemma4 teatral, qwen3 directo) | Cambiar de modelo cambia comportamiento y tono: evaluar ambos caminos |
| 3 | En CPU, el primer uso del modelo grande incluye su carga en Ollama | El ruteo tiene costo de latencia cuando se alternan modelos |
| 4 | Dynamic prompts: no hay tools; cambia el system prompt según el context | Primero identificar **qué perilla** se gira (modelo, prompt o tools) |
| 5 | El system prompt dinámico no aparece en `messages` | Para auditar prompts: trace de LangSmith o un middleware espía |

## 🎯 Para el examen
- `@wrap_model_call` recibe `(request, handler)`; **debe** llamar `handler(request)` y devolver su resultado.
- `request.override(...)` devuelve un **request nuevo** (no muta el original). Campos: `model`, `messages`, `system_message`, `tools`, `tool_choice`, `response_format`, `model_settings`.
- `request.messages` = atajo de `request.state["messages"]`.
- El `model=` de `create_agent` es el valor por defecto; el middleware puede reemplazarlo en cada llamada.
- Criterios de ruteo típicos: largo de la conversación, tipo de usuario, dificultad, modalidad (imágenes), *fallback*.
- `@dynamic_prompt` = atajo sobre `wrap_model_call`; la función devuelve `str` o `SystemMessage`; los datos vienen de `request.runtime.context` (definido con `context_schema`) o de `request.state`.
- El system prompt dinámico **no** se guarda en el state (`messages`).
- **Trampa:** el modelo elegido se ve en `response_metadata["model_name"]` / metadata del trace, no como una tool.
