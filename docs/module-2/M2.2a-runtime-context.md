# M2.2a Runtime Context

## Resumen
- El **runtime context** son datos que se pasan al agente **en cada invocación**, por fuera de los mensajes: `agent.invoke({...}, context=ColourContext(...))`.
- Se declara su forma con `create_agent(..., context_schema=ColourContext)`. Suele ser un `@dataclass` (o TypedDict / Pydantic).
- **El modelo no ve el context.** Solo lo leen las **tools** (con `ToolRuntime`) o el **middleware**.
- Sirve para datos de la sesión o del usuario que no deben ir en el prompt: `user_id`, permisos, preferencias, conexiones a BD, API keys por usuario.

## Código clave
```python
from dataclasses import dataclass
from langchain.tools import tool, ToolRuntime

@dataclass
class ColourContext:
    favourite_colour: str = "blue"
    least_favourite_colour: str = "yellow"

@tool
def get_favourite_colour(runtime: ToolRuntime[ColourContext]) -> str:
    """Get the favourite colour of the user"""
    return runtime.context.favourite_colour     # ← la tool lee el context

agent = create_agent(model=get_model("gemma4:latest"),
                     tools=[get_favourite_colour],
                     context_schema=ColourContext)

agent.invoke({"messages": [HumanMessage("What is my favourite colour?")]},
             context=ColourContext(favourite_colour="green"))
```
- `runtime: ToolRuntime[...]` **no aparece en el esquema de la tool**, así que el modelo no lo ve ni lo rellena. LangChain lo inyecta al ejecutar la tool.

## Experimento del notebook
| Agente | ¿Tiene tools? | Resultado esperado |
|---|---|---|
| `context_schema` sin tools | ❌ | El modelo **no sabe** tu color: el context existe pero no le llega |
| Con `get_favourite_colour` + `ToolRuntime` | ✅ | Llama la tool y responde "blue" |
| Igual, con `context=ColourContext(favourite_colour="green")` | ✅ | Responde "green": el mismo agente cambia según el context de **esa** invocación |

## Context vs State vs Memoria (para no confundir)
| | Runtime **context** | **State** (M2.2b) | **Memoria** (checkpointer) |
|---|---|---|---|
| Qué es | Datos fijos de la invocación | Datos del grafo que **cambian** durante la ejecución | Historial guardado por `thread_id` |
| Quién lo pone | El que llama (`context=...`) | Nodos y tools (pueden actualizarlo) | El checkpointer, automático |
| ¿Lo ve el modelo? | No, solo tools y middleware | Los `messages` sí; campos extra solo vía tools y middleware | Sí, los mensajes previos |
| ¿Persiste? | No, solo esa invocación | Durante el run (y en el checkpoint si hay) | Sí, entre invocaciones del mismo thread |

## Resultados ✅ (todo como se esperaba)
| Prueba | Mensajes | Respuesta | Tokens / tiempo |
|---|---|---|---|
| 1. Agente **sin tools** + `context=ColourContext()` | Human → AI | *"I do not know what your favourite colour is…"* | 15 entrada · 9,7 s (7 s cargando gemma4) |
| 2. **Con tools** + `ColourContext()` | Human → AI `get_favourite_colour(args={})` → Tool `"blue"` → AI | *"The user's favourite colour is blue."* | 85 + 108 entrada · ~3,5 s |
| 3. Con tools + `ColourContext(favourite_colour="green")` | Igual | *"…is green."* | ~2 s |

**Lo que confirma cada prueba:**
1. El context **no llega al modelo**: estaba en el runtime y el modelo respondió que no sabía.
2. El tool call salió con **`args: {}`**: el parámetro `runtime: ToolRuntime` no está en el esquema que ve el modelo; LangChain lo inyecta al ejecutar.
3. **Mismo agente, distinto context, distinta respuesta**: el context es por invocación, no hay que recrear el agente.
4. El valor del context **sí entra al historial**, pero solo como resultado de la tool (`ToolMessage → green`). Si no hay tool, no aparece en ningún mensaje.

Comparado con M2.1, todo es rápido: los mensajes son cortos (85–108 tokens de entrada), así que en CPU cada paso tarda ~1 s.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | El agente sin tools no sabía el color aunque se pasó `context` | El context no se inyecta en el prompt | Darle una tool que lea `runtime.context` (o middleware) | **Context = para tools y middleware, no para el modelo** |
| 2 | ¿Cómo sabe la tool el color si el modelo no le pasa argumentos? | `ToolRuntime` se inyecta en la ejecución; no está en el esquema | Ver `args: {}` en el tool call | Los parámetros `runtime` son invisibles para el modelo, así que no puede falsificarlos |
| 3 | Cambiar el usuario sin recrear el agente | El context es por `invoke` | `invoke(..., context=ColourContext(favourite_colour="green"))` | Un agente sirve para N usuarios; el context lleva quién es cada uno |

## 🎯 Para el examen (dominio Build)
- **Dos piezas:** `context_schema=MiContext` al **crear** el agente y `context=MiContext(...)` en **cada** `invoke`/`ainvoke`.
- **Quién ve el context:** tools (`runtime.context`) y middleware. **El modelo no.**
- **`ToolRuntime[T]`** da acceso a: `context`, `state`, `store`, `stream_writer`, `tool_call_id` y `config`.
- **El parámetro `runtime` no forma parte del esquema de la tool** (el modelo manda `args: {}`). Es seguro: el modelo no puede inventar ni cambiar el context.
- **El context es inmutable durante el run.** Si algo tiene que cambiar → **state** (`Command(update=...)`, ver [M2.2b State](M2.2b-state.md)).
- **Context no persiste** entre invocaciones; la **memoria** (checkpointer + thread_id) sí.
- **Caso de uso típico:** `user_id`, rol y permisos, idioma, conexión a la BD o al tenant → las tools filtran datos por usuario (seguridad multiusuario, ver [M1.5 Memory](../module-1/M1.5-memory.md)).
- **Pregunta trampa probable:** "¿Cómo hace el agente para responder con un dato del context?" → mediante una tool o middleware que lo lea. Pasarlo en `context` no basta.

## Trampas para el examen
- `context_schema` en `create_agent` + `context=` en `invoke`.
- `ToolRuntime[T]` da acceso a `runtime.context`. También a `runtime.state`, `runtime.store` y `runtime.stream_writer`.
- El context es **inmutable** durante el run; para algo que cambie, usar state.
- Aplicado a multiusuario ([M1.5 Memory](../module-1/M1.5-memory.md)): el `user_id` puede ir en el context y las tools lo usan para filtrar datos del usuario.
