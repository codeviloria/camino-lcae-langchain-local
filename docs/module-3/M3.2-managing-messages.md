# M3.2 Managing Messages (summarization y trim)

## Resumen
Dos formas de controlar **qué historial ve el modelo**, ambas como **middleware** de `create_agent`:
| Técnica | Mecanismo | Cuándo corre | Qué pierde |
|---|---|---|---|
| **Resumir** | `SummarizationMiddleware(model, trigger, keep)` | `before_model` (antes de **cada** llamada al modelo) si se pasa el `trigger` | El detalle literal de los mensajes viejos (queda un resumen) |
| **Borrar** | `@before_agent` que devuelve `RemoveMessage(id=...)` | Una vez al inicio de cada `invoke` | Todo lo que estaba en los mensajes borrados |

## Conceptos nuevos
### `checkpointer=InMemorySaver()` — la "libreta" del agente
- Guarda una foto (*checkpoint*) del state después de cada paso, por **`thread_id`** (`{"configurable": {"thread_id": "1"}}`).
- Mismo `thread_id` → continúa la conversación. Otro → empieza de cero.
- `InMemory` = RAM del kernel (se pierde al reiniciar). Producción: `SqliteSaver`, `PostgresSaver` o el servidor de LangGraph (en `langgraph dev` **no** se pone checkpointer).
- `agent.get_state(config).values["messages"]` abre la libreta y muestra lo guardado.
- El resumen y el borrado **reescriben** lo guardado en el thread: los mensajes originales ya no existen ahí.

### `SummarizationMiddleware` por dentro (verificado en el código de LangChain 1.4)
- `trigger`: `("tokens", 100)`, `("messages", 50)`, `("fraction", 0.8)` del contexto; lista = OR; dict = AND. El conteo de tokens es **aproximado** (`count_tokens_approximately`).
- `keep=("messages", 1)`: mensajes recientes que se conservan intactos (por defecto 20).
- Devuelve `RemoveMessage(id=REMOVE_ALL_MESSAGES)` + **un `HumanMessage`** *"Here is a summary of the conversation to date: …"* (`additional_kwargs={"lc_source": "summarization"}`) + los mensajes conservados.
- `model=` es el que **escribe el resumen**: puede ser uno más barato que el del agente. Cuesta una llamada extra.

### `@before_agent` + `RemoveMessage`
- `RemoveMessage(id=m.id)` no se envía al modelo: es una **orden de borrado** que aplica el *reducer* `add_messages`.
- El middleware devuelve un `dict` de actualización del state (igual que `Command(update=...)` en una tool).

### 🧒 Leer `response["messages"]` (índices y slicing)
Una lista de Python es una **fila**: el primero es `[0]`; con negativos se cuenta desde el final (`[-1]` = último).
| Escribes | Te da | Uso típico |
|---|---|---|
| `msgs[0]` | el primero | el resumen (esta lección) |
| `msgs[-1]` | el último | **la respuesta final** |
| `msgs[-2]` | el penúltimo | el `ToolMessage` antes de la respuesta |
| `msgs[-3]` | el antepenúltimo | el `AIMessage` con `.tool_calls` (bonus SQL) |
| `msgs[1:]` | todos menos el primero | saltarse el resumen |
| `msgs[-3:]` | los 3 últimos | pregunta → tool → respuesta |
| `len(msgs)` | cuántos | ver si se resumió o borró |

Atributos: `.content` (texto), `.type` (`human`/`ai`/`tool`), `.tool_calls`, `.response_metadata` (modelo, tiempos), `.usage_metadata` (tokens). Se usa `[-1]` y no un número fijo porque el largo de la lista cambia.

## Resultados (gemma4, CPU)
| Parte | Resultado | Evaluación |
|---|---|---|
| Summarization | 9 mensajes → **3**: `[0]` resumen (`HumanMessage`, `lc_source: summarization`), `[1]` última pregunta, `[2]` respuesta | ✅ |
| Calidad del resumen | Conservó los 4 hechos: capital Lunapolis, clima 120 °C / −100 °C, 100.000 mineros, posible huelga por el nuevo presidente | ✅ |
| Costo | Respuesta: 211 tokens de entrada, **782 de salida, 76 s** (la mayor parte generando) | ⚠️ Largo para CPU |
| Trim | 7 mensajes → 5 (se borraron los 2 `ToolMessage`) + respuesta | ✅ |
| Respuesta del trim | *"as an AI, I have no way of knowing the physical temperature"* | ✅ **Esperado**: `temp=42C` estaba solo en un `ToolMessage` borrado |
| Costo trim | 80 tokens de entrada, 175 de salida, 20,6 s (7 s de carga del modelo) | ✅ |

**¿Hay que corregir algo?** No: las dos partes hicieron lo que enseña el curso. Opcional para CPU: un `system_prompt` que pida respuestas breves (782 tokens tardaron 72 s).

## 🧠 Lecciones aprendidas
| # | Observación | Regla |
|---|---|---|
| 1 | El resumen es un `HumanMessage`, no un `SystemMessage` | Para encontrarlo: `msgs[0]` o `additional_kwargs["lc_source"] == "summarization"` |
| 2 | Tras resumir, los mensajes originales desaparecen del thread | Resumir es **con pérdida** e irreversible en el checkpoint |
| 3 | Borrar `ToolMessage`s quitó el dato que el usuario pedía | Recortar ahorra tokens pero puede **quitar la evidencia**; decidir qué se borra según la tarea |
| 4 | `ToolMessage` sin un `AIMessage` con `tool_calls` antes | Muchas APIs rechazan tool messages "huérfanos"; el trim previo evita el error |
| 5 | El resumen agrega una llamada al modelo | En CPU, usar el mismo modelo ya cargado o uno más chico |

## 🎯 Para el examen
- **Dónde corre cada hook:** `before_agent` (1 vez por invoke) vs `before_model` (antes de cada llamada al modelo; ahí vive `SummarizationMiddleware`).
- `trigger` y `keep` aceptan `("tokens", n)`, `("messages", n)` y `("fraction", x)`; el `keep` por defecto son 20 mensajes.
- El resumen entra como **`HumanMessage`** al inicio, precedido de `RemoveMessage(REMOVE_ALL_MESSAGES)`.
- `RemoveMessage(id=...)` borra del state vía el reducer `add_messages`.
- Sin checkpointer no hay memoria entre invocaciones; el `thread_id` separa conversaciones.
- **Trampa:** recortar o resumir mal = el agente "olvida" datos necesarios (aquí, la temperatura).
