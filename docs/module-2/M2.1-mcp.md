# M2.1 MCP (Model Context Protocol)

## Resumen
- **MCP** es un protocolo estándar para que un agente use capacidades que viven **en otro proceso o servidor**: tools, resources y prompts.
- `MultiServerMCPClient` (de `langchain-mcp-adapters`) se conecta a uno o varios servidores MCP y convierte lo que exponen en objetos de LangChain.
- Transporte `stdio`: el cliente **lanza el servidor como un subproceso** y se comunica con él por entrada y salida estándar.
- Lo que expone un servidor MCP:

| Tipo | Qué es | Cómo se obtiene | ¿Lo usa el agente solo? |
|---|---|---|---|
| **Tool** | Función que el modelo puede llamar | `await client.get_tools()` | ✅ se pasa en `tools=` |
| **Resource** | Dato de solo lectura (archivo, URL) | `await client.get_resources("server")` | ❌ hay que inyectarlo uno mismo |
| **Prompt** | Plantilla de prompt | `await client.get_prompt("server", "prompt")` | ❌ se usa como `system_prompt` |

## Adaptaciones al lab local (y por qué)

### 1. Primera celda: `local_model`
```python
import sys, pathlib
sys.path.insert(0, str(next(p for p in [pathlib.Path.cwd(), *pathlib.Path.cwd().parents] if (p / "local_model.py").exists())))
from dotenv import load_dotenv
load_dotenv()
from local_model import get_model
```
**Por qué:** igual que en el módulo 1, el notebook está en `notebooks/module-2/` y `local_model.py` en la raíz del repo.

### 2. Comando del servidor MCP: `"python"` → `sys.executable` (o `uv run python`)
```python
client = MultiServerMCPClient({
    "local_server": {
        "transport": "stdio",
        "command": sys.executable,                     # antes: "python"
        "args": ["resources/2.1_mcp_server.py"],
    }
})
```
**Por qué:** con `stdio`, el servidor MCP es **otro proceso** que lanza el cliente. El comando `"python"` lo resuelve el sistema operativo, no uv:
- En Ubuntu puede no existir (el binario se llama `python3`).
- Si existe, sería el Python del sistema, **sin** `mcp`, `tavily` ni `dotenv` → el servidor muere al arrancar y `get_tools()` falla.

Como Jupyter se lanza con `uv run jupyter lab`, el kernel ya corre en el `.venv` del repo. Verificado:
```python
print(sys.executable)
# <repo>/.venv/bin/python
```
Así que `sys.executable` = el Python de uv → el servidor MCP corre con las mismas librerías que el notebook.

| Opción | Qué ejecuta | Requisito |
|---|---|---|
| `"command": sys.executable` | `.venv/bin/python` directo | Ninguno ✅ |
| `"command": "uv", "args": ["run", "python", …]` | uv activa el mismo `.venv` | `uv` debe estar en el PATH del subproceso; si no → `FileNotFoundError: 'uv'` |
| `"command": "python"` (original) | Python del sistema | ❌ no tiene las dependencias |

### 3. Modelo: `"gpt-5-nano"` → `get_model("gemma4:latest")`
```python
agent = create_agent(model=get_model("gemma4:latest"), tools=tools, system_prompt=prompt)
```
**Por qué:** sin APIs de pago. gemma4 soporta tools y es el más rápido del lab (~10,8 tok/s) — ver [M1.7 Personal Chef](../module-1/M1.7-personal-chef.md).

### 4. Servidor de la hora: mismo Python y zona horaria local
```python
client = MultiServerMCPClient({
    "time": {
        "transport": "stdio",
        "command": sys.executable,
        "args": ["-m", "mcp_server_time", "--local-timezone=America/Bogota"],
    }
})
```
**Por qué:** mismo motivo que el punto 2 (`mcp_server_time` está en el `pyproject.toml`, o sea en el `.venv`). Zona horaria: `America/New_York` → `America/Bogota`.

### Lo que no se cambió
- **Celda "Fix for Windows":** en Linux no hace nada (`sys.platform != "win32"`). Se deja.
- **`await` directo en celdas:** Jupyter lo soporta (event loop propio). En un `.py` habría que usar `asyncio.run(...)`.
- **`resources/2.1_mcp_server.py`:** usa Tavily (ya configurado), no OpenAI. No requiere cambios.

## Trampas detectadas en el notebook original
- **El prompt menciona `github_file` como si fuera una tool**, pero en el servidor es un **resource**. El agente solo recibe `tools` → si el modelo intenta llamar `github_file`, falla. Tools ≠ resources.
- `config={"thread_id": "1"}` sin checkpointer no hace nada (no hay memoria).
- `search_web` devuelve 5 resultados completos de Tavily → en CPU la 2ª llamada al modelo será lenta, como en [M1.4 Web Search](../module-1/M1.4-web-search.md).

## Resultados en el lab

### Servidor MCP local (`2.1_mcp_server.py`) ✅
Pregunta: *"Tell me about the langchain-mcp-adapters library"*

| Paso | Entrada | Salida | Tiempo |
|---|---|---|---|
| Modelo → decide `search_web("langchain-mcp-adapters library")` | 208 | 22 | 11,7 s (6,7 s cargando gemma4) |
| Tool MCP `search_web` (Tavily, en el subproceso) | — | — | ~1 s |
| Modelo → respuesta final | **2.272** | **577** | **89,4 s** |

- El agente llamó la tool MCP igual que una tool normal: `langchain-mcp-adapters` la convierte en un `StructuredTool`.
- El `ToolMessage` de MCP llega distinto: `content` es una **lista de bloques** (`[{"type": "text", ...}]`) y trae un `artifact` con `structured_content` (el resultado como dict).
- No intentó usar `github_file` (el resource): con `search_web` le bastó.
- Otra vez, lo lento es leer los 5 resultados de Tavily (2.272 tokens). Recortar en el servidor con `max_results=3` igual que en [M1.7 Personal Chef](../module-1/M1.7-personal-chef.md).

### Servidor MCP de la hora (`mcp_server_time`) ⚠️
Pregunta: *"What time is it?"* → respuesta: *"What timezone would you like to know the current time for?"* **No llamó la tool.**

Causas:
1. **Se reusó la variable `prompt`** del servidor anterior como `system_prompt`, que dice *"solo respondo sobre LangChain, LangGraph y LangSmith"*. El original del curso crea este agente **sin** `system_prompt`.
2. La tool `get_current_time` **requiere** un argumento `timezone`; ante la duda, el modelo preguntó en vez de usar el valor por defecto.

Solución: crear el agente sin `system_prompt` y preguntar con la zona: *"What time is it in America/Bogota?"*.

## Servidor local vs servidor "online": diferencias
| | Servidor local (`2.1_mcp_server.py`) | Servidor de la hora (`mcp_server_time`) |
|---|---|---|
| **Quién lo escribió** | Yo / el curso, con `FastMCP` | Un tercero: paquete publicado en PyPI |
| **Dónde está el código** | `resources/2.1_mcp_server.py` (lo puedo editar) | Dentro del `.venv` (`python -m mcp_server_time`) |
| **Qué expone** | Tool (`search_web`) + resource (`github_file`) + prompt | Solo tools (`get_current_time`, `convert_time`) |
| **Configuración** | Lee `.env` (`TAVILY_API_KEY`) | Argumentos de línea de comandos (`--local-timezone`) |
| **Transporte** | `stdio` | `stdio` |
| **Dónde corre** | Subproceso en mi máquina | **También subproceso en mi máquina** |

> **Ojo con el nombre "Online MCP" del curso:** el servidor de la hora **no** es remoto. Corre local igual que el otro; lo "online" es que es un servidor **ya hecho del ecosistema MCP** que solo se instala y se lanza. Un servidor realmente remoto usaría `"transport": "streamable_http"` con una `"url"`, sin `command`.

## `await`: qué hace y por qué aparece aquí
- Las funciones `async def` no devuelven el resultado: devuelven una **corrutina**, una tarea pendiente. `await` la ejecuta y **espera su resultado** sin bloquear el event loop, que mientras tanto puede atender otras tareas, como la comunicación con el subproceso MCP.
- En MCP todo es asíncrono: el cliente habla con el servidor por `stdio` o HTTP. Por eso se usa `await client.get_tools()`, `await client.get_resources(...)` y `await client.get_prompt(...)`.
- Las **tools de MCP son solo async**. Por eso el agente se llama con `await agent.ainvoke(...)` y no con `agent.invoke(...)`. Con `invoke`, la tool falla porque no tiene versión síncrona.
- **En Jupyter** se puede escribir `await` directo en la celda, porque el notebook ya tiene un event loop corriendo.
- **En un `.py`** no se puede usar `await` suelto. Hay que envolverlo:
```python
import asyncio

async def main():
    tools = await client.get_tools()
    agent = create_agent(model=get_model("gemma4:latest"), tools=tools)
    return await agent.ainvoke({"messages": [HumanMessage("...")]})

result = asyncio.run(main())
```
- Pares sync/async en LangChain: `invoke` ↔ `ainvoke`, `stream` ↔ `astream`, `batch` ↔ `abatch`.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | `"command": "python"` no garantiza el entorno | El servidor `stdio` es otro proceso; el SO resuelve `python`, no uv | `sys.executable` (verificado = `.venv/bin/python`) o `uv run python` | En MCP `stdio`, lanzar el servidor con el **mismo intérprete** del cliente |
| 2 | El agente de la hora preguntó "¿qué zona horaria?" en vez de llamar la tool | Se reusó `prompt` (rol "solo LangChain") como `system_prompt`, y la tool exige `timezone` | Agente sin `system_prompt`; incluir la zona en la pregunta | Revisar qué variables se arrastran de secciones anteriores del notebook |
| 3 | 89 s en la respuesta final | 5 resultados de Tavily = 2.272 tokens de entrada en CPU | `max_results=3` en el servidor MCP | La latencia de la tool también se controla del lado del servidor MCP |
| 4 | ¿Por qué `await` y `ainvoke`? | El cliente MCP y sus tools son asíncronos | `await` en Jupyter; `asyncio.run()` en un `.py` | Tools MCP → siempre `ainvoke`/`astream` |

## Trampas para el examen
- Las tools de MCP son **async-only** → `ainvoke`. "Online" en el curso ≠ remoto: `stdio` siempre es un subproceso local.
- MCP expone **tools, resources y prompts**; solo las tools se pasan directo al agente.
- Transportes: `stdio` (subproceso local) vs `streamable_http` / `sse` (servidor remoto por URL).
- `MultiServerMCPClient` puede combinar varios servidores en un solo cliente.
- Los métodos son **async** (`await client.get_tools()`, `await agent.ainvoke(...)`).
