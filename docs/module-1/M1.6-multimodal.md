# M1.6 Multimodal Messages

## Resumen
- Un `HumanMessage` puede llevar una **lista de bloques de contenido** en vez de un string: texto, imagen, audio.
- Cada bloque tiene `type` y, para binarios, `base64` + `mime_type`.
- El modelo debe soportar la modalidad (**vision**, **audio**). `qwen3:8b` es solo texto → para este notebook se usa **`gemma4:latest`** (vision + audio + tools).
- Que el modelo soporte una modalidad **no garantiza** que el runtime (Ollama) ni la integración (`langchain-ollama`) la soporten.

## Bloques de contenido
```python
from langchain.messages import HumanMessage

# Texto
HumanMessage(content=[{"type": "text", "text": "What is the capital of The Moon?"}])

# Imagen
HumanMessage(content=[
    {"type": "text", "text": "Tell me about this capital"},
    {"type": "image", "base64": img_b64, "mime_type": "image/png"},
])

# Audio (sintaxis estándar de LangChain — la que entra en el examen)
HumanMessage(content=[
    {"type": "text", "text": "Tell me about this audio file"},
    {"type": "audio", "base64": aud_b64, "mime_type": "audio/wav"},
])
```

## Elegir el modelo según la modalidad
| Modelo | Capabilities (`ollama show`) | Uso |
|---|---|---|
| `qwen3:8b` | completion, tools, thinking | Texto y agentes con tools. **No ve ni oye** |
| `gemma3:4b` | completion, vision | Imagen (rápido). Sin tools ni audio |
| `gemma4:latest` | completion, **vision, audio**, tools, thinking | Este notebook |

## Audio en el lab local: el camino completo
Lo que se probó y qué pasó:

| # | Prueba | Resultado | Diagnóstico |
|---|---|---|---|
| 1 | `sounddevice` | `OSError: PortAudio library not found` | Falta la librería del sistema → `sudo apt install libportaudio2 portaudio19-dev` |
| 2 | LangChain con `{"type": "audio"}` | `ValueError: Blocks of type audio not supported` | **`langchain-ollama` solo convierte bloques de imagen** |
| 3 | API directa `/api/chat` con `"images": [audio]` (44,1 kHz) | "No audio file was provided" | Audio descartado en silencio |
| 4 | Igual, convertido a 16 kHz | "the city of" | **Alucinación**: el audio estaba en silencio (nivel máx = 0.0) |
| 5 | Grabación con el Jabra (`device=5`), 16 kHz, nivel 5212 | "I hear Lino and gusto" | El audio **sí llega**; prompt en inglés para audio en español |
| 6 | **LangChain con bloque `image` + audio 16 kHz + prompt en español** | "Hola, ¿cómo estás? Me llamo Gino. Mucho gusto en saludarte. Mi color favorito es" ✅ | **Funciona.** El corte final es real: la grabación de 6 s terminó ahí |
| 7 | Igual, con `"mime_type": "audio/wav"` | Misma respuesta ✅ | `langchain-ollama` **ignora el `mime_type`**; Ollama detecta el tipo por los bytes |
| 8 | **Grabación nueva** de 10 s con otra frase | "Hoy es 3 de octubre. Saludos." ✅ | **Confirmado** con audio distinto: no era caché ni coincidencia |

### Receta que funcionó
```python
import sounddevice as sd, numpy as np, io, base64
from scipy.io.wavfile import write
from IPython.display import Audio, display

sr, dur = 16000, 10                                   # 16 kHz mono: lo que espera Gemma; 10 s para frases completas
audio = sd.rec(int(dur * sr), samplerate=sr, channels=1, dtype="int16", device=5)  # Jabra
sd.wait()
print("nivel máx:", np.abs(audio).max())              # int16: >1000 = hay voz
display(Audio(audio[:, 0], rate=sr))                  # escuchar antes de enviar

buf = io.BytesIO(); write(buf, sr, audio)
aud16_b64 = base64.b64encode(buf.getvalue()).decode()

agent = create_agent(model=get_model("gemma4:latest"))
q = HumanMessage(content=[
    {"type": "text", "text": "Transcribe exactamente, palabra por palabra, lo que se dice en este audio en español."},
    {"type": "image", "base64": aud16_b64, "mime_type": "audio/wav"},   # workaround: audio por el campo images (mime_type se ignora)
])
print(agent.invoke({"messages": [q]})["messages"][-1].content)
```

> ⚠️ **Workaround, no producción.** Funciona porque `ChatOllama` pone los bloques `image` en el campo `images` de Ollama, y Ollama detecta el tipo real por los bytes. Puede romperse si cambia cualquiera de los dos. Para producción: **Whisper → texto → agente**.

## Las 3 capas de una capacidad multimodal
| Capa | ¿Soporta audio? |
|---|---|
| 1. Modelo (pesos Gemma 4) | ✅ |
| 2. Runtime (Ollama → llama-server) | ✅ por el campo `images`, con audio 16 kHz mono |
| 3. Integración (`langchain-ollama`) | ❌ rechaza `{"type": "audio"}` |

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | qwen3 no sirve para imagen/audio | Modelo solo texto | `get_model("gemma4:latest")` | Revisar `ollama show` → Capabilities antes de elegir modelo |
| 2 | `OSError: PortAudio library not found` | `sounddevice` necesita una librería del sistema | `apt install libportaudio2 portaudio19-dev` + reiniciar kernel | Algunos paquetes Python dependen de librerías del SO |
| 3 | `Blocks of type audio not supported` | `langchain-ollama` solo traduce bloques de imagen | Workaround con bloque `image`, o API directa, o Whisper | **Capacidad del modelo ≠ soporte de la integración**: revisar las 3 capas |
| 4 | El modelo "transcribió" un audio mudo ("the city of", "Transcribe", "un perro") | Se grababa del dispositivo `default`, no del micrófono → nivel 0.0 | `sd.query_devices()` → `device=5` (Jabra) | **Verificar la entrada antes de culpar al modelo**: nivel y reproducir |
| 5 | Un modelo multimodal no dice "no oigo nada" | Alucina a partir del prompt (repitió "Transcribe") | Prompt neutral ("What words do you hear?") para probar | Si la respuesta copia palabras del prompt, sospechar alucinación |
| 6 | Audio a 44,1 kHz descartado en silencio | Gemma espera 16 kHz mono | Grabar directo a 16 kHz | Formato de audio para Gemma: **16 kHz, mono, WAV** |
| 7 | Transcripción pobre ("Lino", "gusto") | Prompt en inglés, audio en español | Pedir en español: "Transcribe exactamente, palabra por palabra…" | El idioma del prompt debe coincidir con el del audio |
| 8 | `NameError: HumanMessage` / `aud_b64` | Reinicio del kernel borra imports y variables | Run All desde arriba | Después de reiniciar, correr todo |
| 11 | Imagen de 2,1 MB → muchos tokens de entrada | Cada imagen se convierte en tokens visuales; en CPU eso es latencia | Reducir resolución antes de enviar | En local, achicar imágenes igual que se recortan resultados de tools |
| 10 | Dos corridas dieron respuesta idéntica: ¿KV cache? | `temperature=0` → misma entrada, misma salida. La KV cache solo acelera, no cambia el resultado ni es memoria | Probar con una grabación nueva | Para validar, cambiar la entrada, no repetirla |
| 9 | Se usó `aud_b64` (viejo, mudo) en vez de `aud16_b64` | Variables con nombres parecidos | Nombres claros y una sola variable de audio | Revisar qué variable se envía |

## ¿Por qué base64?
- La petición viaja como **JSON**, que solo admite texto. Base64 convierte los bytes del WAV en texto seguro; Ollama lo decodifica y recupera los bytes exactos (**no degrada el audio**).
- Costo: el tamaño crece ~33 % (3 bytes → 4 caracteres). 10 s a 16 kHz ≈ 320 KB WAV → ≈ 430 KB en base64.
- Alternativas para archivos grandes: `url` (el proveedor descarga), `file_id` (subida previa en APIs como OpenAI/Anthropic), o ruta local + tool.

## `mime_type` según el proveedor
| Proveedor | Uso del `mime_type` |
|---|---|
| **Ollama** | Se ignora: su API solo tiene `images` (lista de base64) y detecta el tipo por los bytes |
| **OpenAI** | Arma el data URL `data:image/png;base64,...` o `format: "wav"` para audio |
| **Anthropic** | `media_type`, validado por la API |
| **Gemini** | `inline_data.mime_type`: decide si procesa imagen, audio, video o PDF |

> Un `mime_type` incorrecto en la nube da **error 400** o se interpreta mal. **El truco audio-como-imagen solo sirve con Ollama.** Buena práctica: poner siempre el `mime_type` correcto para que el código sea portable.

## Trampas para el examen
- Bloques estándar de LangChain v1: `{"type": "text"}`, `{"type": "image"}`, `{"type": "audio"}`, `{"type": "file"}` con `base64`/`url` + `mime_type`.
- El soporte de cada bloque **depende del proveedor** (integración), no solo del modelo.
- `content` puede ser string o lista de bloques.
