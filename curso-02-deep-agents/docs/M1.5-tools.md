# M1.5 · Tools

> **Estado:** ✅ · **Fecha:** 2026-10-06 · **Labs:** `python/m1/m1.5_scratch_agent_tools.py`, `m1.5_homework_filled.py` · **Modelo:** Nemotron 3 Ultra (OpenRouter `:free`)

## 🧸 La idea en simple
Una tool es una herramienta en la caja del agente. El modelo **no la usa con sus manos**: escribe un pedido (`tool_calls`) y el runner de Tools ejecuta la función y le devuelve el resultado. El docstring es la etiqueta de la herramienta: si la etiqueta es mala, el modelo no sabe cuándo usarla.

## 📚 Conceptos clave
- `@tool` convierte una función de Python en tool. **Nombre + docstring + tipos de argumentos** = lo que lee el modelo.
- `tools=[...]` es **aditivo**: se suma a los built-ins (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`, `execute`, `task`). No reemplaza nada.
- `write_todos` es aparte y opt-in (`TodoListMiddleware`). `execute` solo funciona con un backend sandbox (M2).
- Flujo: `AIMessage(tool_calls=[...])` → Tools ejecuta → `ToolMessage` → el modelo sigue.
- `tool_calls` es una **lista**: el modelo puede pedir varias tools en paralelo en el mismo turno.
- Tools de **acción** (enviar, borrar) necesitan control → HITL (M1.8).

## 🎯 Para el examen
- ¿Quién ejecuta la tool? **No el LLM**: el LLM emite `tool_calls`, el nodo Tools la ejecuta.
- Trampa: "`tools=` reemplaza las tools por defecto". Falso, es aditivo.
- Lo más importante para que el modelo elija bien una tool es la **descripción (docstring)**.
- En la tool, captura errores y devuélvelos como texto (`"Error: ..."`) para que el agente corrija y reintente.

## 🧠 Mnemotecnia
**"El LLM pide, Tools hace":** el modelo es el cliente, no el cocinero.
