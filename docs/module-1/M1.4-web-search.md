# M1.4 Web Search

## Resumen
- El conocimiento del modelo se congela en su fecha de corte; para datos actuales necesita una **tool de búsqueda**.
- **Tavily** es una API de búsqueda hecha para agentes: devuelve resultados ya limpios (`title`, `url`, `content`, `score`) listos para pasar al LLM.
- Se envuelve en una tool con `@tool` y se agrega con `create_agent(model, tools=[web_search])`.
- El agente decide **solo** cuándo buscar: con una pregunta sobre el presente, llamó a `web_search` sin que el prompt lo pidiera.

## Experimento: sin tool vs con tool
| | Sin web search | Con Tavily |
|---|---|---|
| "How up to date is your training?" | "Hasta octubre 2024" | — |
| "Who is the actual president of Colombia?" | **Álvaro Uribe Vélez, reelegido en mayo 2022** ❌ (falso: en 2022 ganó Petro, y Uribe no puede ser reelegido) | **Abelardo de la Espriella, desde el 7 ago 2026** ✅ con fuentes |

> Sin tool, el modelo no dice "no sé": **inventa con seguridad**. Esa es la razón de ser de las tools de búsqueda y de RAG.

## Código mínimo
```python
from langchain.tools import tool
from typing import Dict, Any
from tavily import TavilyClient

tavily_client = TavilyClient()          # lee TAVILY_API_KEY del .env

@tool
def web_search(query: str) -> Dict[str, Any]:
    """Search the web for information"""
    return tavily_client.search(query)

agent = create_agent(model=get_model(), tools=[web_search])
response = agent.invoke({"messages": [HumanMessage("who is actual president of colombia?")]})
response["messages"][1].tool_calls   # → web_search(query='actual president of colombia')
```

### Versión optimizada para CPU (recomendada en mi lab)
```python
@tool
def web_search(query: str) -> list[dict]:
    """Search the web for current information. Use for recent events, people in office, prices or news."""
    r = tavily_client.search(query, max_results=3)
    return [{"title": x["title"], "url": x["url"], "content": x["content"][:500]} for x in r["results"]]
```

## Medición real (qwen3:8b, CPU)
| Paso | Tokens de entrada | Tokens generados | Tiempo |
|---|---|---|---|
| Modelo → decide buscar | 143 | 24 | 8,2 s |
| Tavily | — | — | 1,4 s |
| Modelo → lee resultados y responde | **1.978** | 87 | **79,2 s** (59 s solo leyendo) |

> El cuello de botella no es Tavily ni la generación: es **leer el resultado de la tool**. 5 resultados completos ≈ 1.800 tokens ≈ 1 minuto en CPU.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | Sin tool, el modelo afirmó que el presidente es Uribe "reelegido en 2022" | Conocimiento congelado + el LLM no admite que no sabe | Darle una tool de búsqueda | Para datos actuales: tool o RAG, nunca la memoria del modelo |
| 2 | La segunda llamada al modelo tardó 79 s | Tavily devuelve 5 resultados completos → 1.978 tokens de entrada; en CPU se leen a ~33 tok/s | `max_results=3` y recortar `content`; devolver solo `title`, `url`, `content` | En local, **el tamaño de la salida de la tool es latencia**. Recortar antes de devolver |
| 3 | `TavilyClient()` sin argumentos funcionó | Lee `TAVILY_API_KEY` del entorno (`load_dotenv`) | Poner la key en `.env`, nunca en el código | Mismo patrón que LangSmith: keys en `.env` |
| 4 | La celda de la tool se ejecutó dos veces | Copia duplicada en el notebook | Solo gasta créditos de Tavily | Cada `invoke` de una tool con API externa cuesta créditos |

## Trampas para el examen
- El modelo elige la tool por su **nombre y docstring**: "Search the web for information" es genérico; describir **cuándo** usarla mejora la decisión.
- La tool devuelve un `dict` → LangChain lo serializa a JSON en el `ToolMessage`.
- Más contexto en el `ToolMessage` = más tokens = más costo y latencia (tema de **context engineering**).
- El trace público en LangSmith muestra cada paso; útil para depurar (dominio Monitor).
