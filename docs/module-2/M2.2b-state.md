# M2.2b State

## Resumen
- El **state** es la "memoria de trabajo" del agente: por defecto contiene `messages`, y se puede **extender** con campos propios.
- Se declara heredando de `AgentState` y se pasa con `create_agent(..., state_schema=CustomState)`.
- **Escribir:** una tool devuelve `Command(update={"campo": valor, "messages": [ToolMessage(...)]})`.
- **Leer:** una tool usa `runtime.state["campo"]`.
- Con checkpointer, el state **persiste por `thread_id`**: lo que guardó un turno lo lee el siguiente.

## Código clave
```python
class CustomState(AgentState):
    favourite_colour: str

@tool
def update_favourite_colour(favourite_colour: str, runtime: ToolRuntime) -> Command:
    return Command(update={"favourite_colour": favourite_colour,
        "messages": [ToolMessage("Successfully updated favourite colour", tool_call_id=runtime.tool_call_id)]})

@tool
def read_favourite_colour(runtime: ToolRuntime) -> str:
    return runtime.state.get("favourite_colour", "No favourite colour found in state")
```
- El `ToolMessage` con `tool_call_id` es **obligatorio** dentro del `Command`: cada tool call necesita su respuesta en `messages`.
- También se puede inicializar el state desde la invocación: `agent.invoke({"messages": [...], "favourite_colour": "green"}, config)`.

## Context vs State (resumen)
| | Context ([M2.2a Runtime Context](M2.2a-runtime-context.md)) | State |
|---|---|---|
| ¿Cambia en el run? | No | Sí (`Command(update=...)`) |
| ¿Persiste por thread? | No | Sí, con checkpointer |
| Uso típico | user_id, permisos, config | datos que el agente descubre en la conversación |

## Resultados
| Prueba | Qué pasó | State final |
|---|---|---|
| 1. *"My favourite colour is green"* (thread 1) | Llamó `update_favourite_colour(favourite_colour="green")` → `ToolMessage("Successfully updated…")` | `favourite_colour: 'green'` ✅ |
| 2. *"Hello, how are you?"* + `"favourite_colour": "green"` en el **input** (thread 10) | No usó tools; respondió el saludo | `favourite_colour: 'green'` ✅ (inicializado desde la invocación) |
| 3. Agente nuevo con `read_favourite_colour`, *"My favourite colour is green"* (thread 1) | Escribió el state otra vez | `'green'` ✅ |
| 4. *"What's my favourite colour?"* (mismo thread 1) | Llamó `read_favourite_colour(args={})` → `ToolMessage("green")` | `'green'` ✅ (leído del checkpoint del turno anterior) |

**Lo que confirma:**
- **Escribir** el state con `Command(update=...)` funciona. El `response` trae el campo propio (`'favourite_colour': 'green'`) junto a `messages`.
- **Leer** el state en un turno posterior funciona porque el checkpointer lo guardó por `thread_id`.
- El state se puede **inicializar desde el input** del `invoke`, sin tools (prueba 2).
- La prueba 3 empezó de cero aunque usaba `thread_id="1"`: el agente nuevo trae su propio `InMemorySaver()`, así que **cada checkpointer es una memoria distinta**.

### ⚠️ Hallazgo: gemma4 devolvió respuestas finales vacías
En las pruebas 1, 3 y 4, el último `AIMessage` llegó con **`content=''` y `output_tokens: 1`**. El state se actualizó y se leyó bien, pero el modelo **no le dijo nada al usuario** (por ejemplo "Tu color favorito es verde").
- En [M2.2a Runtime Context](M2.2a-runtime-context.md), con un patrón casi igual (tool → `ToolMessage("blue")`), gemma4 sí respondió con texto. La diferencia es que aquí no hay system prompt y la tool no devuelve una pregunta clara para el usuario.
- **Cómo detectarlo:** en el trace de LangSmith el último paso muestra **1 token de salida**; en el notebook, `response["messages"][-1].content == ""`.
- **Arreglos a probar:**
  1. system prompt: *"After using a tool, always reply to the user in one sentence."*
  2. comparar con `get_model("qwen3:8b")`.
- **Regla:** en un agente, que la tool funcione no garantiza que el usuario reciba respuesta. **Validar siempre el contenido del último mensaje** (es un caso para evaluar en el dominio Test).

## 🎯 Para el examen (dominio Build)
- **Extender el state:** `class CustomState(AgentState): campo: tipo` → `create_agent(..., state_schema=CustomState)`. `AgentState` ya trae `messages`.
- **Escribir desde una tool:** devolver `Command(update={"campo": valor, "messages": [ToolMessage(..., tool_call_id=runtime.tool_call_id)]})`.
  - El **`ToolMessage` con `tool_call_id` es obligatorio**: cada tool call necesita su respuesta en `messages`, o el siguiente paso del modelo falla.
  - `Command` viene de `langgraph.types`.
- **Leer desde una tool:** `runtime.state["campo"]`. Usar `.get()` o `try/except KeyError`, porque el campo puede no existir todavía.
- **Inicializar desde el input:** `agent.invoke({"messages": [...], "campo": valor}, config)`.
- **Persistencia:** el state se guarda en el **checkpoint** del `thread_id`. Sin checkpointer, no sobrevive entre `invoke`.
- **El `response`** de `invoke` es el **state completo** (`messages` + campos propios).
- **Context vs State:** context = inmutable y por invocación, para datos del que llama. State = mutable y por thread, para lo que el agente descubre.
- **`runtime` (ToolRuntime) es invisible para el modelo** (`args: {}`), igual que en M2.2a.
- **Pregunta trampa probable:** "¿Qué devuelve una tool que actualiza el state?" → un `Command`, no un string. Y debe incluir el `ToolMessage`.

## 🧠 Lecciones aprendidas
| # | Problema | Causa | Solución | Regla |
|---|---|---|---|---|
| 1 | La respuesta final de gemma4 llegó vacía (`content=''`, 1 token) | Sin system prompt, gemma4 cierra el turno después de la tool sin redactar respuesta | System prompt que exija responder; comparar con qwen3 | Validar el último mensaje; el trace muestra `output_tokens: 1` |
| 2 | La prueba 3 en `thread_id="1"` no traía el historial de la prueba 1 | Agente nuevo = `InMemorySaver()` nuevo | Reusar el mismo checkpointer si se quiere continuar | La memoria vive en el checkpointer, no en el `thread_id` solo |
| 3 | El state se puede pasar en el input | `invoke({"messages": [...], "favourite_colour": "green"})` | — | Útil para precargar datos conocidos sin gastar un tool call |

## Trampas para el examen
- `state_schema` (state del agente) ≠ `context_schema` (datos de la invocación).
- Las tools escriben el state con `Command(update=...)`, no con `return valor`.
- Sin checkpointer, el state no sobrevive entre `invoke`.
